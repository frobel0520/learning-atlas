Field Manual · 一個 HTTPS 請求的實地手冊

請求的一生

你在網址列輸入 https://todo.example.com 按下 Enter，大約兩百毫秒後畫面出現。這段時間裡，一個請求依序經過瀏覽器、DNS、TCP、TLS、HTTP、Nginx、FastAPI、資料庫，再帶著資料回到 React，畫成你看到的畫面。這本手冊沿著同一個請求走完全程，每一站都有可以動手做的實驗。

  • 11 章，約 2.5 小時，可以分次讀
  • 加密、SQL、React 都在你的瀏覽器裡真的執行
  • 每章 3 題測驗，全對算完成，進度只存在這台裝置

一次請求的路線

0ms

    每站的時間由下方實驗 0-1 的設定算出。點任一站可以直接看說明。

    RTT 是網路的時間單位

    RTT（Round-Trip Time）是封包去程加回程的時間。台北到東京約 30–40 ms，到美西約 130–160 ms。光速有上限，RTT 很難靠升級主機縮短，所以協定設計都在想辦法少來回幾趟。

    握手就是在對齊共識

    TCP 握手對齊「序號從哪開始」，TLS 握手對齊「用哪把鑰匙加密、對方是不是本人」。每次握手至少花一個 RTT，所以重用連線非常重要。

    每一層只管自己的事

    IP 只管送到哪台機器，TCP 只管完整送達，TLS 只管加密，HTTP 只管請求的語意。出問題時先判斷是哪一層，除錯就少走一半的路（第 10 章有整理）。

    實驗 0-1

    時間花在哪：一次載入的瀑布圖

    欄位和 Chrome DevTools → Network → 點一個請求 → Timing 分頁一樣。拉動 RTT，看哪幾段跟著變長；再切換協定和連線狀態，看能省下幾趟來回。

    連線狀態

    模型假設：DNS 查詢花 1 個 RTT；下載時間只算「大小 ÷ 頻寬」，沒有計入 TCP 慢啟動，所以大檔案在高 RTT 下實際會更慢。

    第 1 站 · 瀏覽器與 DNS · 約 12 分鐘

    瀏覽器先讀懂網址，再問出 IP

    按下 Enter 後，瀏覽器先判斷你輸入的是網址還是搜尋字；確定是網址後，把它拆成協定、主機、埠號、路徑，先翻自己的快取，沒有才上網。上網的第一件事是問 DNS：這個名字對應哪個 IP。

    一句話：網址告訴瀏覽器「用什麼方式、去哪台機器、要什麼東西」；DNS 把好記的名字換成機器用的 IP。

    HSTS：強制走 HTTPS

    網站回過 Strict-Transport-Security 標頭後，瀏覽器會記住它。下次你打 http://，瀏覽器在送出前就自動改成 https://，不給中間人機會。

    快取先查，再上網

    順序大致是 Service Worker → 記憶體快取 → 磁碟快取。命中就直接用，DevTools 的 Size 欄位會顯示 (memory cache) 或 (disk cache)。第 4 站會實驗快取規則。

    Origin 是安全邊界

    Origin = 協定 + 主機 + 埠號。Cookie、localStorage、能不能讀別人的回應（CORS），都以 origin 為單位。三者有一個不同就是不同來源。

      第 2 站 · IP 與 TCP · 約 15 分鐘

      把資料切成封包，送到對的機器

      拿到 IP 後，瀏覽器請作業系統開一條 TCP 連線。HTTP 請求會被一層層包裝：TLS 加密、TCP 編上序號、IP 寫上收件地址，最後由 Wi-Fi 或網路線送出去。中間的路由器只看 IP 標頭，一站一站轉送。

      一句話：IP 負責「送到哪台機器」，但不保證送到；TCP 在兩端用序號和確認，補上「完整、按順序」。

      IP：盡力而為

      每個封包獨立找路，可能遺失、重複、亂序。路由器每轉一次就把 TTL 減 1，減到 0 就丟掉，避免封包在網路上繞圈。家裡的 192.168.x.x 是私有 IP，出門時由路由器做 NAT 換成公網 IP。

      TCP：可靠的位元組流

      • 序號 + 確認：知道哪些位元組到了
      • 重傳：逾時沒收到確認就再送一次
      • 流量控制：接收端說自己還能收多少
      • 壅塞控制：發現掉包就放慢

      Port 與四元組

      一條 TCP 連線由（來源 IP、來源 port、目的 IP、目的 port）決定。瀏覽器同時開三條連線到 203.0.113.10:443，作業系統會給三個不同的來源 port（例如 52344、52345、52346）來區分。

      實驗 2-1

      封裝：一個 HTTP 回應被包了幾層

      乙太網路一個封包最多帶 1500 位元組（MTU）。扣掉 IP 和 TCP 標頭，每段最多 1460 位元組資料（MSS）。拉動大小，看要切成幾個封包、多少比例花在標頭上。

      實驗 2-2

      IPv4 標頭的 20 個位元組

      每列 32 個位元。點一個欄位，看它在我們這個請求裡的值與用途。

      實驗 2-3

      TTL 與 traceroute

      從你的電腦到伺服器要經過 8 台路由器。設定封包出發時的 TTL，看它死在哪一站。traceroute 就是把 TTL 從 1 開始逐次加 1，收集每一站回的「逾時」通知，拼出整條路徑。

      實驗 2-4

      TCP 的一生：握手、傳資料、掉包重傳、揮手

      左邊是瀏覽器，右邊是伺服器。每個箭頭是一個 TCP 區段，兩側是連線狀態。打開「掉一個封包」，看 TCP 怎麼補救。

      TCP 與 UDP

      TCPUDP
      連線先握手才傳資料直接送
      可靠性保證送達、按順序、不重複不保證，掉了就掉了
      標頭20–60 位元組8 位元組
      典型用途HTTP/1.1、HTTP/2、SSH、資料庫連線DNS 查詢、影音通話、遊戲、QUIC（HTTP/3）

      HTTP/3 改用 UDP 不是放棄可靠性，而是把重傳、排序、加密都搬進 QUIC 協定自己做。好處是一條串流掉包不會卡住其他串流，第 4 站有動畫。

      第 3 站 · TLS 與 HTTPS · 約 15 分鐘

      在公開的網路上，講只有兩個人懂的話

      TCP 連上之後、HTTP 送出之前，瀏覽器和伺服器先做 TLS 握手：交換一次性的公鑰、各自算出相同的祕密、確認伺服器的憑證是真的。之後所有 HTTP 內容都用這把對稱金鑰加密。HTTPS 就是「HTTP 跑在 TLS 裡面」。

      一句話：非對稱加密用來「安全地約定一把鑰匙」和「證明身分」，真正的資料用又快又強的對稱加密。

      三個保證

      • 機密性：竊聽者只看到亂碼
      • 完整性：改一個位元，解密就失敗
      • 身分驗證：憑證證明「這把公鑰屬於 todo.example.com」

      前向保密（ECDHE）

      每條連線都產生全新的臨時金鑰對，用完即丟。就算伺服器的憑證私鑰日後外洩，過去錄下來的流量也解不開。TLS 1.3 只允許這種金鑰交換方式。

      憑證鏈

      伺服器憑證由中繼 CA 簽、中繼 CA 由根 CA 簽，根 CA 內建在作業系統和瀏覽器的信任清單裡。Let's Encrypt 提供免費憑證，有效期目前預設 90 天（業界正逐步縮短），一律用 certbot 之類的工具自動續期。

      實驗 3-1

      TLS 握手訊息，一則一則看

      🔒 表示這則訊息已經加密。注意 TLS 1.3 從 ServerHello 之後就開始加密，連憑證都是加密傳送的。切換到 TLS 1.2 比較來回次數。

      實驗 3-2

      金鑰交換：公開喊話，卻得到只有兩人知道的祕密

      這裡用瀏覽器內建的 Web Crypto 真的執行 ECDH（P-256 曲線，也是 TLS 支援的曲線之一）、HKDF 和 AES-GCM。每按一次都是全新的隨機金鑰。

      第 4 站 · HTTP · 約 18 分鐘
      
      
      請求與回應：一問一答的文字協定
      
      
      加密通道建好後，瀏覽器送出真正的 HTTP 請求：方法、路徑、一堆標頭，可能再加一段本文。伺服器回一個狀態碼、標頭和本文。HTTP 本身不記得你是誰（無狀態），登入狀態靠 Cookie 或 Token 每次帶上。
      
      
      一句話：HTTP 規定「要做什麼」（方法）、「對誰做」（路徑）、「附帶條件」（標頭），回應用狀態碼說明結果。
      
    
      

    
      
      
      
        
      狀態碼看第一位
      
        
        
          
      • 2xx 成功：200、201 已建立、204 無內容
        • 
          
      • 3xx 去別處：301/308 永久、302/307 暫時、304 用快取
        • 
          
      • 4xx 你的錯：400、401、403、404、422、429
        • 
          
      • 5xx 伺服器的錯：500、502、503、504
        • 
        
      
      
      
      
      
        
      Cookie 的安全屬性
      
        
        
          
      • HttpOnly：JavaScript 讀不到，降低 XSS 偷 session 的風險
        • 
          
      • Secure：只在 HTTPS 送
        • 
          
      • SameSite=Lax：跨站的 POST 不帶 Cookie，擋大部分 CSRF
        • 
        
      
      
      
      
      
        
      版本差在傳輸方式
      
        
      HTTP/1.1 是純文字，一條連線一次一個請求，瀏覽器對同一主機最多開 6 條。HTTP/2 改成二進位框架，一條連線同時跑多個串流。HTTP/3 把 HTTP/2 搬到 QUIC（UDP）上。三者的方法、狀態碼、標頭意義都一樣。

      方法的兩個性質
      
    
      
      
      
        
      方法用途安全（不改資料）冪等（重送 N 次＝送 1 次）

      第 5 站 · Nginx · 約 15 分鐘
      
      
      站在門口的總機：反向代理
      
      
      請求抵達伺服器的 443 port，第一個接手的是 Nginx。它負責解開 TLS、依網址路徑決定交給誰：/api/ 開頭的轉給後面的 FastAPI，其他的直接從磁碟回傳 React 打包好的檔案。外界只看得到 Nginx，看不到後面有幾台應用程式伺服器。
      
      
      一句話：Nginx 用 location 規則決定每個請求的去向，用 proxy_pass 把它轉給後端。
      
    
      

    
      
      
      
        
      為什麼前面要放 Nginx
      
        
        
          
      • TLS 終止：憑證集中管理，後端只講 HTTP
        • 
          
      • 靜態檔：傳檔案比 Python 快很多
        • 
          
      • 負載平衡、限流、gzip、上傳大小限制
        • 
          
      • 前後端同一個網域，不需要 CORS
        • 
        
      
      
      
      
      
        
      後端怎麼知道真正的客戶端 IP
      
        
      對 FastAPI 來說，連線是從 Nginx（127.0.0.1）來的。Nginx 用 X-Forwarded-For、X-Real-IP、X-Forwarded-Proto 把原始資訊轉告後端。uvicorn 只信任指定來源的這些標頭，不然任何人都能偽造。
      
      
      
      
      
        
      單頁應用的 try_files
      
        
      React Router 的 /todos/42 在磁碟上沒有對應檔案。try_files $uri $uri/ /index.html 讓找不到的路徑都回 index.html，交給前端路由處理。少了這行，重新整理就會 404。

      第 6 站 · FastAPI 後端 · 約 15 分鐘
      
      
      型別就是規格：FastAPI 怎麼處理一個請求
      
      
      Nginx 把請求轉到 127.0.0.1:8000，在那裡聽的是 uvicorn。uvicorn 把 TCP 上的位元組解析成 HTTP，交給 FastAPI 應用程式：比對路由、把路徑和查詢參數轉成正確型別、用 Pydantic 驗證 JSON 本文、注入資料庫連線，最後呼叫你寫的函式，把回傳值轉成 JSON。
      
      
      一句話：你用 Python 型別宣告「要什麼資料」，FastAPI 幫你做解析、驗證、錯誤訊息和 API 文件。
      
    
      

    
      
      
      
        
      ASGI 分層
      
        
      uvicorn（伺服器：處理 socket 與 HTTP 解析）→ Starlette（路由、中介層、請求物件）→ FastAPI（依型別解析參數、驗證、OpenAPI）→ 你的函式。打開 /docs 就有自動產生的互動文件。
      
      
      
      
      
        
      驗證失敗一律 422
      
        
      參數型別不對、少欄位、字串太長，FastAPI 都在呼叫你的函式之前就擋下，回 422 和一個 detail 陣列。loc 告訴你錯在哪：["body", "title"]、["path", "todo_id"]。
      
      
      
      
      
        
      依賴注入
      
        
      Depends(get_db) 讓每個請求拿到自己的資料庫連線。get_db 用 yield 交出連線，回應送出後執行 finally 關閉，不會漏關。測試時可以換成假的資料庫。

        第 7 站 · 資料庫 · 約 18 分鐘
        
      
        資料真正住的地方
        
      
        FastAPI 的函式執行 SELECT id, title, done FROM todos。資料庫負責把資料安全地存在磁碟、讓很多請求同時讀寫也不會互相踩到、在資料量變大時還能很快找到你要的那一筆。這一站的實驗都用真正的 SQLite（編譯成 JavaScript 跑在你的瀏覽器裡）。
        
      
        一句話：資料庫用「約束」守住資料正確、用「交易」保證全有或全無、用「索引」換取查詢速度。
        
      
        SQLite 引擎：載入中…
        
    
        

    
        
      
        
        
        約束是最後一道防線
        
        
        PRIMARY KEY 唯一識別、NOT NULL 不可空、UNIQUE 不重複、FOREIGN KEY 參照必須存在。前端和後端都驗證過，資料庫還是要守，因為總有程式會繞過它們。
        
      
        
      
        
        
        ACID
        
        
          
          
        • Atomicity：交易內全部成功或全部撤銷
          • 
          
        • Consistency：約束永遠成立
          • 
          
        • Isolation：同時執行的交易不互相干擾
          • 
          
        • Durability：COMMIT 後斷電也不會不見
          • 
        
        
      
        
      
        
        
        連線池
        
        
        建立資料庫連線要 TCP 握手、驗證身分，PostgreSQL 每條連線還是一個獨立行程。應用程式維持一組連線重複使用（SQLAlchemy 預設 5 條），不要每個請求都重新連。

          第 8 站 · React 與瀏覽器渲染 · 約 15 分鐘
          
      
          回應回到瀏覽器，變成畫面
          
      
          JSON 回到瀏覽器後，React 元件把它存進 state。state 一變，React 重新執行元件函式算出新的畫面描述，和上一次比較，只把差異寫進真正的 DOM。接著瀏覽器重新計算樣式與版面、繪製，你才看到新的一列待辦。
          
      
          一句話：React 的畫面 = f(state)。你只改 state，React 負責算出要動哪些 DOM；瀏覽器再把 DOM 畫成像素。
          
    
          

    
          
      
          
        
          瀏覽器的渲染管線
          
        
          HTML 解析成 DOM、CSS 解析成 CSSOM → 合成 Render Tree → Layout（算位置大小）→ Paint（畫像素）→ Composite（合成圖層）。越前面的階段被觸發，後面全部都要重做。
          
      
          
      
          
        
          事件迴圈
          
        
          JavaScript 在主執行緒上一次只做一件事。同步程式先跑完，然後清空所有微任務（Promise），再拿一個巨集任務（setTimeout、點擊事件）。主執行緒被長任務卡住，畫面就凍結。
          
      
          
      
          
        
          CSR 與 SSR
          
        
          Vite 做的 React 是 CSR：Nginx 回傳幾乎空白的 index.html，JavaScript 下載完才畫出內容。Next.js 這類 SSR 在伺服器先產生 HTML，首屏較快、SEO 較好，但需要一台 Node 伺服器。
          
      
          
    
          

    
          
      
          
        實驗 8-1
        
          改哪個屬性，瀏覽器要重做哪幾段
